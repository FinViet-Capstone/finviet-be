## 1. Transactions: wallet-type-conditional editable fields

**Problem**: `PUT /transactions/{id}` (`UpdateTransactionDto`) only ever accepts `categoryId`
today, for every transaction regardless of source wallet. Product intent: a transaction
sourced from a `sepay_linked` wallet must stay read-only except for category (its
amount/date/merchant are provider-authoritative, from bank sync) — but a transaction on a
`basic` wallet (manual/photo/CSV/SMS entry) should be fully editable, matching what the
manual-entry flow itself allows at creation time.

**Proposed change**: extend `UpdateTransactionDto` to `{ categoryId?, amount?, merchant?, transactionDate? }`.

**Validation**:
- Existing checks stay: transaction must exist and be owned (404 either way, no
  existence-leak); `EnsureNotTransfer` still blocks editing `transfer_out`/`transfer_in` legs
  entirely (422 `transfer_managed`, unchanged — transfers stay fully locked regardless of
  wallet type).
- New: if the transaction's wallet has `walletType == "sepay_linked"`, reject any of
  `amount`/`merchant`/`transactionDate` being present in the request body — 422, new code
  `synced_transaction_fields_locked`, message along the lines of "Only the category can be
  changed for transactions from a bank-synced wallet." (mirrors the existing
  `linked_wallet_read_only` / `synced_transaction_locked` pattern used elsewhere for
  sepay-sourced transactions).
- If `amount` provided: `amount <= 0` → 400 (same rule as create).
- If `categoryId` provided: re-validate with the same rules as create (`category_type_mismatch`,
  `goal_transaction_locked` for `cat_savings_goal`, 404 for unknown category, `cat_income` →
  `cat_income_other` remap).

**Business logic**:
- Runs in a DB transaction with the same wallet row-lock pattern as create/delete.
- If `amount` changed: reverse the old balance delta on the wallet, apply the new one;
  would-go-negative → 422 `insufficient_balance` (same code as create, reused).
- `walletId` and `transactionType` remain immutable (out of scope for this change — only
  amount/merchant/date/category become editable, never which wallet or income-vs-expense).
- If the resulting/unchanged type is `expense`, re-sync budgets for that month (same as
  `PATCH /classify` today).

## 2. Savings Goals: ledger rework (history + withdraw + per-action wallet choice + notes)

These four are grouped because they all touch the same underlying ledger table
(`SavingGoalContribution`, already used internally by contribute/delete) and are easiest to
design/ship together.

### 2a. Contribution/withdrawal history endpoint

**New endpoint**: `GET /saving-goals/{id}/contributions` (role: Customer).

**Validation**: goal must exist and be owned by the caller → 404 (no existence-leak, same
pattern as other goal endpoints).

**Response**: `SavingGoalContributionResponse[]`:
```ts
{ contributionId, goalId, amount, type: "contribution" | "withdrawal", contributedAt, note?, transactionId? }
```
Ordered newest (`contributedAt`) first.

**Business logic**: reads the existing `SavingGoalContribution` table, filtered to the goal.
Requires the `type` column added in 2b below (existing rows backfilled as `"contribution"`).

### 2b. Withdraw-to-wallet endpoint

**New endpoint**: `POST /saving-goals/{id}/withdraw` (role: Customer, requires
`Idempotency-Key` — same pattern as `/contribute`).

**Request**: `WithdrawSavingGoalRequest { amount, walletId, note? }` — `walletId` is
**required on every call** (see 2c for why there's no goal-level default for withdrawal).

**Validation**:
- `amount <= 0` → 400.
- `amount > currentAmount` → 422, new code `goal_withdraw_exceeds_saved` ("Cannot withdraw
  more than the goal's current saved amount.").
- `walletId` must belong to the customer and not be deleted → 404 if not.
- `walletId` must **not** be `sepay_linked` → 422, new code
  `goal_withdraw_target_sepay_unsupported` ("Withdrawals can only go to a regular wallet, not
  a bank-linked one.") — same rationale as the existing wallet-level withdraw feature:
  crediting a bank-synced wallet manually would desync it from the real account.

**Business logic**: DB transaction, row-locks the goal and the target wallet (same locking
pattern as `/contribute`). Credits `wallet.balance += amount` (an `income` transaction,
`categoryId = cat_savings_goal`, linked via the contribution row's `transactionId`).
Decrements `goal.currentAmount -= amount`. Inserts a `SavingGoalContribution` row with
`type = "withdrawal"`, `amount` stored positive (direction comes from `type`, not sign).
Re-evaluates `isCompleted = currentAmount >= targetAmount` — a withdrawal can drop a
completed goal back to incomplete.

### 2c. Per-action wallet choice (no static 1-goal-1-wallet binding)

**Problem**: today `CreateSavingGoalRequest.fundingWalletId` is set once at creation and
`ContributeSavingGoalRequest` has no way to override it (`{ amount }` only) — every
contribution is forced through whatever wallet was chosen at creation time, and
`UpdateSavingGoalRequest` can't change it either. Product decision: **reject the static
binding model entirely.** A goal should not have one permanent funding wallet; the user
picks how much and from which wallet on every contribution (and to which wallet on every
withdrawal — see 2b). Do not build a "change the goal's funding wallet" PATCH feature — the
fix is per-action wallet choice, not making the static field editable.

**Proposed change**: `ContributeSavingGoalRequest` gains `fundingWalletId?: Guid`.

**Validation**: if provided, must belong to the customer, not be deleted, and not be
`sepay_linked` (422 `insufficient_balance`-adjacent — reuse whatever code the create-time
funding-wallet check already uses for a `sepay_linked` funding wallet, for consistency).

**Business logic**:
1. Wallet resolution order: request's `fundingWalletId` if provided → else the goal's stored
   `fundingWalletId` (creation-time default, kept only as an optional pre-fill/fallback,
   never the sole mechanism) → else no wallet at all.
2. If a wallet resolved: lock it, check `balance >= amount` (422 `insufficient_balance` if
   short), debit it, record the expense `Transaction` + `SavingGoalContribution` linking the
   two, same as today.
3. If no wallet resolved (neither request nor goal has one): `currentAmount` still increments
   with no wallet touched — unchanged from today's existing behavior.

This is additive and backward-compatible: existing clients that never send
`fundingWalletId` keep exactly today's behavior (fall back to the goal's stored default).

### 2d. Contribution note field

**Proposed change**: `ContributeSavingGoalRequest.note?: string` (suggest capping at 280
chars for consistency with other short free-text fields elsewhere in the API, though no
FluentValidation validators exist in this feature area today — team's call). Persist on
`SavingGoalContribution.note`. Apply the same field to `WithdrawSavingGoalRequest` (2b) for
symmetry — a withdrawal should be able to carry a note too.

## Schema note

2a–2d together imply two new columns on the existing `SavingGoalContribution` table:
`type` (enum/string, default `'contribution'` for all existing rows — a migration backfill,
not a breaking change) and `note` (nullable string). No new table needed; the ledger already
exists, it's just under-exposed and under-parameterized today.

## 3. Income allocation: no arbitrary-month lookup (discovered while wiring §A of the FE plan)

**Problem**: `GET /profile/income-allocation` only ever resolves `current` (today's calendar
month) and `pending` (next month) — there's no way to ask "what was the income/allocation
split in effect for month X?" for an arbitrary past or future month. The backend already has
this exact resolution logic internally (`ResolveEffectiveRow` — "the row with the largest
`effectiveMonth <= month`, else the customer's live default columns" — used by both
`GET /budgets` and `GET /budgets/buckets?month=`), it's just not exposed as a standalone
answer outside those two budget endpoints.

**Impact today**: worked around on the FE side — `app/(tabs)/budgets/index.tsx` (the one
screen that needs a specific past month's split) now sources its numbers from
`GET /budgets/buckets?month=` instead of the profile endpoint, since that already resolves
correctly per-month. Every other caller only ever asks for the current month, so this isn't
blocking anything today.

**Proposed change** (nice-to-have, not urgent): add an optional `month` query param to
`GET /profile/income-allocation` that runs the same `ResolveEffectiveRow` logic against an
arbitrary `yyyy-MM`, defaulting to today's month when omitted (preserving current behavior).
Would let the FE simplify `real/incomeAllocation.ts`'s `getEffectiveIncomeAllocation(month)`
to be precise for any month instead of only the current one.
